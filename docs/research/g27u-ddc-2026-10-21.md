# REDMI G27U 双模切换：本机 DDC/CI 实测

日期：2026-10-21。目标：在无澎湃 OS 的 REDMI G27U 上，通过电脑切换 4K 160Hz 与 1080p 320Hz。

## 结论

**本次没有找到经验证可用的软件双模切换指令。** DDC/CI 读写链路工作正常，但对两种硬件模式的完整 Get VCP 扫描，没有找到随竞技模式开关变化的可写控制项。

该结果不能证明不存在只写指令、其他报文格式、其他源地址或厂商私有协议。当前不能把一个经过验证的 G27U 双模开关接入 MonitorBar。

## 环境与状态

- macOS，Apple Silicon；系统显示名称为 `Mi Monitor`。
- CoreGraphics 显示器 ID 为 `2`，厂商 ID 为 `25001`，产品 ID 为 `10164`（`0x27B4`）。
- 4K 模式的系统序列值为 `1`，竞技模式为 `7`。这说明在本机观察到的显示器身份信息也随硬件模式改变。
- DDC 能力字符串报告固件 `V1.0.28`，MCCS `2.2a`；VCP `DF` 的数值回复却为 `0x0201`，因此版本信息并不完全一致。
- IOKit `DCPAVServiceProxy` 的外接 IOAVService 可访问，采用 I²C 目标地址 `0x37`、子地址 `0x51`。
- VCP 输入源读数为 `0x10`；按 MCCS 输入源定义对应 DisplayPort 2。

## 系统模式实测

1. 显示器关闭竞技模式时：当前为 3840×2160、160Hz，逻辑桌面为 1920×1080 HiDPI；枚举模式中没有 320Hz。
2. 用户在实体菜单开启竞技模式后：系统出现原生 1920×1080、320Hz 模式；通过 CoreGraphics 成功切换并读取确认。
3. 竞技模式下没有枚举出 4K 模式。
4. 用户在实体菜单关闭竞技模式后：系统恢复 3840×2160、160Hz，逻辑桌面恢复 1920×1080 HiDPI。

因此，系统显示模式选择已经验证可行；本次研究的缺口是显示器自身的硬件双模开关。

## 全量 VCP 对比

在两种模式下分别读取 `0x00` 至 `0xFF` 共 256 个编码。只发送 Get VCP 请求（负载 `01 <code>`），检查回复校验和、操作码、功能码和结果字段。每次都得到：

| 回复分类 | 数量 |
| --- | ---: |
| 标准 VCP 成功回复 | 46 |
| 标准 VCP 不支持回复（result=1） | 209 |
| 其他格式回复 | 1 |

“成功回复”只表示协议字段通过检查，不保证该项存在完整的可读写实现，也不保证字段都有实际意义。

两份扫描记录的字段差异只有：

| VCP | 1080p 320Hz：current / maximum | 4K 160Hz：current / maximum | 标准含义 |
| --- | --- | --- | --- |
| `AC` | `35920 / 5` | `25220 / 5` | 水平扫描频率，只读 |
| `AE` | `31895 / 0` | `16041 / 0` | 垂直扫描频率，只读 |

这些读数反映当前扫描时序，不是可写的竞技模式开关。其原始字段也不应直接当作整数 Hz。

值得核查的项目：

| VCP | 两种模式的读数 | 解释或限制 |
| --- | --- | --- |
| `03` | 标准回复明确返回不支持 | 标准 Soft Controls，不能据此直接套用其他显示器的菜单按键序列 |
| `B1` | 标准回复明确返回不支持 | LG 个别双模显示器使用的厂商编码；没有 G27U 适用证据 |
| `B4` | `1 / 2` | 标准 Source Timing Mode，两种硬件模式未出现字段差异；MCCS 版本间格式不同 |
| `DC` | `0 / 255` | 标准 Display Mode，不能仅凭名称推断为分辨率双模 |
| `E3` | `0 / 1` | 未在能力字符串声明的厂商项，两种模式读数相同，含义未确认 |
| `E6` | `0 / 1` | 同上 |
| `FA` | `0 / 65535` | 厂商项，无双模状态差异 |
| `FB` | 非标准 VCP 回复 | 有效长度内为 `6E 82 01 FB 46`；不是标准 `02` 操作码的 Get VCP 回复 |
| `FD` | `116 / 65535` | 厂商项，含义未确认 |
| `FF` | 全量扫描为 `0 / 65535` | 单独连续探测时可出现与前项相同的字段，不能作为可靠状态判断 |

在 4K 状态下，针对 `03/B1/B4/E3/E6/FA/FB/FD/FF` 又连续读取三轮；`03` 和 `B1` 均重复返回不支持，`E3/E6` 均保持 0。`FB` 的原始日志打印 11 字节，但只有前 5 字节属于该短回复，后面的字节不能据此解码为控制状态。

## 写入链路验证

对已知的亮度 VCP `10` 进行一次可恢复测试：

```text
读取原亮度：34 / 100
写入：35
回读：35，验证成功
写回：34
回读：34，恢复成功
```

这验证了当前连接与 IOAVService 的 Set VCP 路径实际可用。它没有验证任何厂商双模写入指令；本次唯一写入的 VCP 设置是亮度。

测试结束时再次读取 CoreGraphics：逻辑 1920×1080、像素 3840×2160、160Hz，显示器背光读数为 34。

## 公开资料核查

- [ddcutil 功能定义](https://www.ddcutil.com/vcpinfo_output/)：`03` 是 Soft Controls；`AC/AE` 是只读扫描频率；`B0` 是保存/恢复设置，不能因为名称是 Settings 就当作双模开关。
- [ASUS 双模切换实现](https://github.com/Gunther-Schulz/ddc-mode-switcher)：其 ASUS XG27JCG 示例通过 `03` 发送特定菜单序列。这只能证明该型号的实现，不能推导 G27U 也接受相同命令。
- [ColorControl 发布说明](https://github.com/Maassoft/ColorControl/releases)：LG 45GX950A 的双模可使用 `B1=8448/8704`。这是特定型号的厂商约定，不能转用于 G27U。
- 通过 G27U、REDMI/Xiaomi、DDC、VCP、双模/竞技模式等组合查询，没有找到可核验的 G27U 双模控制编码。

后续若获得 G27U 厂商协议、对应固件的静态分析结果，或同型号官方控制软件的通信记录，可以据此构造有依据的写入测试。本次完整扫描不能排除这些尚未识别的路径。
